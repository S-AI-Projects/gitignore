1. PATTERN MECHANICS
──────────────────────────────────────────────

The rule is a bare name without a leading slash or trailing slash:

    EIFGENs

Gitignore bare-name semantics:
  • A pattern with no slash at all is matched against the filename component
    at EVERY directory depth (gitignore(5) §PATTERN FORMAT).
  • It therefore ignores any directory named exactly "EIFGENs" regardless of
    how deeply it is nested, and also any file named exactly "EIFGENs".
  • Files *inside* an ignored directory are implicitly ignored too (Git stops
    descending into ignored directories).
  • The match is an exact whole-name match; "EIFGENs-backup", "EIFGENs_extra",
    and "EIGENS" do NOT match.

4. TRACKED-FILE BEHAVIOUR
──────────────────────────────────────────────

Setup:
  project/EIFGENs/tracked.e was force-added (git add -f) and committed
  before the .gitignore was committed to the index.

Observations:
  a) git ls-files project/EIFGENs/tracked.e  → file is in the index (tracked).
  b) git check-ignore -v project/EIFGENs/tracked.e  → exit 1, NOT reported as
     ignored. Git skips ignore-checking for tracked paths.
  c) git check-ignore -v --no-index project/EIFGENs/tracked.e  → exit 0,
     pattern IS reported (.gitignore:2:EIFGENs). The --no-index flag bypasses
     the index-lookup and applies pure pattern matching.
  d) git status shows the tracked file as clean (not flagged as ignored),
     confirming that tracking takes priority over .gitignore rules.

Conclusion: once a file is tracked, .gitignore does not cause Git to drop it.
Developers who accidentally track files inside EIFGENs must use
"git rm --cached" to stop tracking them.
